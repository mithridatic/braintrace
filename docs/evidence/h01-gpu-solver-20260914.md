# H01 GPU tree elimination qualification

The complete default 104-cell evolution under 30 seconds remains **not achieved**.
This change accelerates physical execution without changing dt, precision,
learning updates, corpus, structural operations, or the linear system solved.

## Change

For supported 32-wide CUDA schedules, execute all leaf-to-root elimination
levels inside one Pallas/Triton kernel with one warp per RHS batch. Preserve
masked atomic additions, level order, and a barrier between levels. Invoke it
only in the primal and transpose callbacks of the existing implicit linear
solve. Other schedules/platforms and installations without the Triton extension
retain the scan solver. Invalid padding updates are explicitly dropped.

The kernel does not replace the model, change temporal resolution, or change
the pp-prop approximation. Existing pinned manifests must be regenerated for
new runs because the implementation hashes change. Old checkpoint continuation
remains tied to its original implementation.

## Vast.ai measurements

RTX 4090; JAX 0.11.0; Python 3.14.7. Another session's evolution remained active,
so these small samples are not isolated statistical benchmarks. The real probe
uses four anatomical cells, 75,605 compartments, dt=0.000625 ms, 160 substeps per
event, and float64. Each phase is synchronized and cProfile-instrumented.

| Phase | Scan baseline | GPU kernel |
| --- | ---: | ---: |
| Cold event including compilation | 27.808 s | 14.456 s |
| Warm event | 17.936 s | 4.479 s |
| Sparse graph construction | 3.171 s | 3.356 s |
| First synthetic one-event Muon update | Incomplete in capped experiment | 107.653 s |
| Warm synthetic one-event Muon update | Not reached | 24.862 s |

The real warm event improved approximately 4x. The GPU probe completed with
finite events, two finite updates, finite optimizer/factors, and peak host RSS
4,728,436 KiB. This does not establish a host-RAM improvement over baseline,
whose learning phase did not complete. These one-event losses are synthetic
squared-logit objectives, not ARC training scores. A complete ARC episode has
many events, so a 24.862-second one-event update is not a 30-second evolution.

The two recorded event voltage vectors match the previously measured scan/drop
version exactly (maximum difference 0 mV). Initial construction and initialization
still cost tens of seconds even for this four-cell subset; they were not changed.

## Validation

- Five-file integration gate: 49 passed in 66.27 s with `pytest -n 2`.
  Includes existing tree/dense/derivative, E/I trace, circuit-event, calcium,
  network step, and ARC execution checks.
- Added 32-wide branched-cell test: two sparse updates match the scan's losses,
  gradient norms, parameters, Muon state, eligibility factors, and voltage
  within rtol=1e-10/atol=1e-11. Passed in 14.27 s with xdist.
- Focused tests cover direct RHS batching, vmap, both Jacobian modes against
  dense solves, input non-mutation, neutral sentinel state, unsupported width,
  explicit CPU execution, and missing Triton-extension fallback.
  Final focused gate: 7 passed in 15.48 s with `pytest -n 2`; the new solver
  module covers 37 of 41 statements (90.24%).
- Windows CPU-only JAX 0.11.1: direct 32-wide CPU fallback check matches the
  scan exactly. Local pytest was unavailable; its package feed returned 401.
  All pytest qualification was performed on Vast.ai with xdist.
- Coverage uses a filesystem source path. The module-name coverage invocation
  aborted before test output; the same gate without coverage and the focused
  filesystem-coverage gate completed. Do not treat aborted instrumentation as
  a test pass.

## Corrections and remaining work

The exact default 104-cell evolution command was attempted with an external
30-second cap on Vast.ai and exited 124 without completing. Its log was empty,
so no internal stage can be inferred. A separate manifest retained all numerical
settings and active cells while updating the implementation hash for this code;
the original manifest and other session's process were preserved. The first
timing wrapper failed because `/usr/bin/time` was absent; the actual gate used
GNU `timeout -k 5 30`. This is a failed completion gate, not a runtime estimate.

The first platform-dispatch implementation assumed the Triton extension could
be imported while tracing the CUDA branch. Windows CPU-only JAX disproved that
assumption. A failing missing-extension regression was added, then a cached
capability check and scan fallback repaired it. Platform dispatch alone does
not remove the need to make every traced branch import-safe.

The full 104-cell command, its runtime, and ARC quality remain unqualified at
the requested 30-second threshold. The next substantial candidates are reducing
cross-cell kernel-launch serialization and accelerating construction, while
preserving sparse dependency analysis and all existing mathematical contracts.
